# PwL — Play with Lovers

Native iOS app (SwiftUI) with a set of small games for couples.
**Core idea:** each partner plays on **their own iPhone** and the two devices connect to play together. The app never uses split-screen or pass-and-play on one device.
**Couples only.** There is no single-player mode and no guest/anonymous login. Every game is a two-player match, so don't add solo modes or single-player features.
Flow: **Loading → login (Google, or PwL ID after the first Google login) → Main tabs (Dashboard · Games · Scoreboard · Settings)**. Games tab: game list → setup (connect to your love) → game.
Every user has a unique 8-character **PwL ID**. To match, one person enters the other's ID in Settings, which sends a **request**. The other person must accept it (or decline it). A user can have only **one love at a time** and must unpair before matching someone else.
UI wording: call the other person **"your love"**, not "partner" or "player 2".

## Tech stack
- Swift 6 (strict concurrency), SwiftUI, iOS 17+, iPhone only, light mode. Portrait everywhere except the Onet match, which is landscape. Info.plist allows both orientations, and `OrientationLock` (`Core/OrientationLock.swift`, reported through `AppDelegate`) picks per screen: call `OrientationLock.set(.landscape)` on appear and `.set(.portrait)` on disappear.
- Observation (`@Observable`) for state. No Combine and no `ObservableObject`.
- Dependencies, both via SPM in `project.yml`: **Firebase** (FirebaseAuth, FirebaseFirestore) 12.x and **GoogleSignIn** 9.x. Don't add others without a good reason.
- Music is synthesized with `AVAudioEngine`, so there are no audio assets.
- Project file is generated by **XcodeGen** from `project.yml`. Do not hand-edit `PwL.xcodeproj`.
  Edit `project.yml`, then run `xcodegen generate`. New files under `PwL/` or `PwLTests/` are picked up automatically after regenerating.

## Conventions (keep these consistent)
- **Design tokens.** All colors, gradients, radii and spacing come from `Theme`. Do not hard-code `Color(...)` in views; add a token instead.
  Use the `.rounded` font design everywhere (`.font(.system(..., design: .rounded))`).
- **Shared components first.** Use `PrimaryButtonStyle` / `SecondaryButtonStyle`, `.card()`, `ChipButton` and `ModalCard` before writing new styling.
- **Every game screen** must:
  - use `GameControlBar` (menu, ?, music, pause), with the timer/counter in its center slot;
  - hide the nav bar (`.toolbar(.hidden, for: .navigationBar)`) and leave the game only through its menu (Resume / Restart / Change settings / Quit);
  - pause when menu or help opens, when the pause button is tapped, and when `scenePhase` is not `.active`;
  - call `audio.setMusicActive(status == .playing)` and `setMusicActive(false)` on disappear;
  - give haptics through `.sensoryFeedback`.
- **Game engine vs. view.** Game logic goes in an `@MainActor @Observable final class <Name>Game` with no SwiftUI import.
  Time-based methods take `at now: Date = .now` so tests control the clock. Randomness goes through `inout some RandomNumberGenerator` so tests can seed it.
- **Navigation.** Add a case to `Route` (AppState.swift), handle it in `MainTabView`'s Games `navigationDestination`, and push with `appState.path.append(...)`. Switch tabs with `appState.selectedTab`.
  Game screens also hide the tab bar (`.toolbar(.hidden, for: .tabBar)`).
- **Adding a game.** Create `Games/<Name>/`, add a `Route` case, and add a `GameInfo` entry in `GameListView.swift`. Add engine tests in `PwLTests/`.
- **Accounts.** Views read `@Environment(AccountStore.self)`: `account`, `love`, `stats`, `nickname`, `loveNickname`, `playerNames`, `isPaired`. Never call Firebase from views. Add the operation to `AccountBackend`, implement it in **both** `FirebaseAccountBackend` and `LocalAccountBackend`, and expose it on `AccountStore`.
- **Persistence.** Use small `struct ...Store` wrappers over `UserDefaults` that take a `defaults` parameter, so tests can inject a fresh suite. `@AppStorage` is fine for remembering UI choices.
- **Concurrency.** UI state is `@MainActor`. Anything that runs on the audio thread is created in a `nonisolated` context (see `AudioManager.makeSourceNode`).
  MultipeerConnectivity delegate callbacks hop to the main actor. Non-Sendable values are wrapped in `Unchecked` for that hop.
  Firestore calls live in `nonisolated static` helpers of `FirebaseAccountBackend`, so transaction and listener closures are never MainActor-isolated. Listener results are hopped back with `Task { @MainActor in … }`.
- **Accessibility.** Icon-only buttons need an `accessibilityLabel`. Tap targets are at least 40pt.

## Multiplayer (two devices)
- `NearbyService` (`Core/Multiplayer`) uses MultipeerConnectivity, so it works over Wi-Fi or Bluetooth with no server. The service type is `pwl-game`.
  - One player calls `host(as:uid:loveUID:)` and the other calls `browse(as:uid:loveUID:)` then `join(_:)`. A room accepts exactly one person.
  - Only the matched love can connect. Hosts advertise their account `uid`, browsers list only hosts whose uid is their `partnerUID`, and the host accepts an invitation only when its context (the guest's uid) is its love.
  - Names are exchanged with a lobby-level `hello`, which sets `partnerName`.
  - **A connection belongs to one game's lobby.** `PartnerConnectionCard(gameID:)` passes the game ID to `host`/`browse` (it is in the discovery info), so rooms are only listed to browsers in the same game.
    Going back to the game list (`appState.path` becomes empty, watched in `MainTabView`) or tapping Leave calls `leaveLobby()`, which sends `bye` and then disconnects.
    The partner shows "{name} left the lobby" (`nearby.notice`), so "connected" always means both of you are in the same lobby. Game screens treat any `!nearby.isConnected` as "connection lost".
  - It is injected with `.environment(nearby)`. `PartnerConnectionCard` is the shared create/join UI.
- Games send their own `Codable` message enum with `nearby.send(_:)`. The screen that currently owns the match sets `nearby.onGameMessage`. The setup screen sets it to receive `.start`, and the game screen sets it on appear.
- **Host is the referee.** Player 0 is the host and player 1 is the guest.
  - The host creates a random **seed** and sends it with the settings. Both devices build the same board and order through `SeededGenerator`. Never use `SystemRandomNumberGenerator` for shared game state.
  - The guest validates locally (`check`). Wrong taps are applied locally and mirrored to the host (`mistake`). Correct taps are sent as `claim`.
  - The host calls `claim(_:by:)` (first one wins) and broadcasts `found`. The guest applies it with `applyFound`.
  - `pause`, `resume`, `restart(seed)` and `leave` are mirrored on both devices. Losing the link or a `leave` message shows a "partner left" overlay.
- After a finished game the **host** calls `account.recordGame(seconds:)`, which updates the couple's Dashboard stats.
- Testing it needs two devices on the same network, for example the iPhone and the simulator (the free team allows up to 3 devices). Engine sync is unit-tested by driving two engine instances with the same seed (`guestMirrorsHostDecisions…`).
- Future: playing over the internet needs a relay or backend, or Game Center (paid developer account). Keep the message enums transport-agnostic so another transport can replace `NearbyService`.

## Games
### Find Numbers (`Games/FindNumbers`)
- Setup choices:
  - Connect with your partner first (`PartnerConnectionCard`). The host chooses the settings and the guest waits.
  - Count: the presets 50/100/150/200 or a custom count from 5 to 500.
  - Order: **1→N**, **N→1** or **Random**. Random means the engine shuffles the find order (`FindNumbersConfig.makeSequence`), and `game.target` reads from `game.sequence`.
  - Number size: Mixed / Small / Big.
- **Race.** Both players hunt for the same target at the same time. The first correct tap (as decided by the host) scores the point. The number then gets a pen-style circle (`PenCircle`) in the finder's `Theme.playerColor` on both devices.
  - A wrong tap counts as a mistake and locks that player for `mistakeLockout` (0.8s).
  - `missesBeforeBlock` (5) wrong taps in a row block that player for `missBlock` (10s, on the game clock, so pausing freezes it). Finding a number resets the streak (`missStreak`). The view shows a countdown from `blockRemaining(for:at:)`.
  - Winner (`FindNumbersGame.winner`): most points, then fewest mistakes, then fastest average reaction.
  - Per-player stats (`PlayerStats`): points, mistakes, reaction time (from the target appearing to the find), and fastest find.
- `FindNumbersBoardGenerator` places numbers on a jittered grid (columns ≈ √(count × 0.66)) with a random scale, rotation (±40°) and palette color. This gives a "scattered worksheet" look without overlaps.
- Numbers containing 6 or 9 are underlined so the reader can tell which way is up.
- The board fits the screen when the cells are at least 40pt. Otherwise it scrolls in 2D, and pinch zooms between 0.6× and 2.5×.
- Lifetime per-player metrics are stored in `PlayerRecordsStore` (`Core/PlayerRecords.swift`), keyed by game ID and player name: games, duels, wins, found, mistakes, time and fastest find. `Features/Scoreboard` shows them. Future competitive games should reuse this store with their own `gameID`.

### Caro (`Games/Caro`)
- Vietnamese gomoku on squared exercise-book paper. Players take turns, and the first to get **5 in a row** (across, down or diagonal) wins.
- The board is always **100×100** (`CaroConfig.boardSize`).
- Setup choice (the host picks):
  - Rule: **Free** (five or more wins) or **Vietnamese** (`blockedEnds`: a line blocked by the opponent at both ends doesn't win; the board edge doesn't count as a block).
- **Turn-based, so there is no referee.** Each device validates its own tap with `CaroGame.place(at:by:)` and sends `move(index)`. The other device applies the same call. Moves that arrive while paused are still applied.
- **Rounds:** round `n` is started by player `n % 2`, who plays X. `restart(round:)` only moves forward, so duplicate restarts are ignored. The series `score` and `draws` are kept until leaving.
- `CaroBoardView` is a viewport, not a scroll view. A `Canvas` draws only the visible squares, because a full 100×100 sheet would be a huge texture.
  The view keeps its own `center` (in squares) and `cell` size (16–64pt): drag moves it, pinch zooms, and taps are mapped back to a cell index.
  It starts at the middle of the board and jumps to a new move that lands off-screen; the scope button goes to the last move. The last move is highlighted and the winning line is struck through.
- Lifetime records are stored in `CaroGame.records` (`gameID` "caro"): games, duels, wins and time. The Scoreboard shows a "Caro wins" card with draws.

### Onet (`Games/Onet`), the "Pikachu" link game
- Tap two tiles with the same face to link them. The link may have at most **3 straight segments (2 turns)** through empty cells, including the ring just outside the board.
  The path search is `OnetGame.path(from:to:in:rows:columns:)`, a breadth-first search by segments that returns the corner points.
- **One board: 9 rows × 16 columns** (`OnetConfig.rows` / `.columns`). That is 144 tiles, so each of the **36 country flags** (`OnetTileFace`) appears exactly 4 times, giving 72 pairs per level. The flags were chosen to look clearly different from each other. They are **not Pokémon art**, which is copyrighted. They sit on raised cream tiles (`Theme.Tile`).
- The match screen is **landscape**: the HUD (level, clock, pairs left, both scores) sits in the `GameControlBar` center and the board takes the rest. The setup screen stays portrait.
- Setup choice (the host picks): levels only. `OnetBoardGenerator` shuffles the 144 tiles and guarantees a playable start.
- **Race like Find Numbers.** There are no turns and no time limit.
  - The guest checks locally (`check`) and sends `claim(first, second)`. The host calls `claim(_:_:by:)`, where the first one wins, and broadcasts `matched` (or `rejected`). The guest applies it with `applyMatch`.
  - Picking two different faces is a mistake with a 0.8s lockout (mirrored with `mistake`). The same face with no path just moves the pick to the new tile.
- **Levels** (setup: 1 level, 3 levels or all 9). `OnetLevel` lists them: 1 Classic, 2 fall down, 3 float up, 4 slide left, 5 slide right, 6 squeeze to the middle, 7 split to the sides, 8 squash to the middle, 9 spread to top and bottom.
  From level 2 on, `slide()` compacts each of `level.lines(rows:columns:)` toward its first cell after every match.
  Clearing a board starts the next level with a board seeded from `seed` plus the level number, so both devices advance in step without a message. Scores add up across levels, and the view shows a "Level N" card for 2s.
  - Tiles have stable `tileIDs`, so the board animates sliding.
  - `revision` is bumped on every board change. The guest sends it with `claim`, and on sliding levels the host rejects claims made on an older board, because the cells may now hold other tiles.
- **Stuck board.** When no pair is linkable, both devices reshuffle the remaining faces with a seed derived from the match seed and `shuffleCount`, so the boards stay identical without a message.
- Winner: most pairs, then fewest mistakes. Records are stored under `OnetGame.records` (`gameID` "onet"), and the Scoreboard shows an "Onet wins" card.

## Accounts & Firebase
- **Login:** Google Sign-In, then Firebase Auth (`FirebaseAccountBackend.signIn`). On first login the account is created with a unique PwL ID. Nickname defaults to the first word of the Google display name.
- **PwL ID login:** after any Google sign-in, `enableCodeSignIn` links a hidden Email/Password credential to the same uid
  (email `<code>@id.pwl.invalid`, password derived from the code). `signIn(code:)` uses it, so the ID alone opens the account.
  Requires **Email/Password** enabled in Firebase Authentication. Anyone who knows the ID can sign in; this was a deliberate product choice.
- **PwL ID** (`AccountCode`): 8 characters from `23456789ABCDEFGHJKMNPQRSTUVWXYZ` (no 0/O/1/I/L). Input is normalized (uppercase, spaces and dashes removed).
- **Firestore model:**
  - `users/{uid}`: code, nickname, email, avatar (≤256px JPEG stored inline as bytes, so there's no Storage bucket), partnerUID, pairID, online, lastOnline, createdAt.
  - `codes/{code}`: `{ uid }`. It is created in the same transaction as the user, which guarantees IDs are unique.
  - `requests/{fromUID}_{toUID}`: from, to, fromNickname, fromCode, toNickname, toCode, createdAt. A pending match request.
  - `pairs/{pairID}`: members, pairedAt, gamesPlayed, secondsPlayed, playDays (`"yyyy-MM-dd"` strings), lastPlayedAt. `pairID` is the two uids sorted and joined with `_`, so a couple who unpair and re-match get their history back.
- **Matching:** `sendRequest` creates `requests/{me}_{love}`. A user has one outgoing request at a time, and a new one replaces the old one. If the other person already asked you, sending accepts their request instead.
  The receiver accepts it (`acceptRequest`) or declines it, and the sender can cancel it. Accepting runs a transaction that pairs both users and deletes the request. It fails if either person already has a `partnerUID`.
  Once a user is paired, `AccountStore` deletes any leftover requests. Unpairing clears both sides.
  `firestore.rules` lets another user set your `partnerUID` to themselves only when you're free **and** `requests/{you}_{them}` exists, and lets them clear it only when it's them. Pending requests show a badge on the Settings tab.
- **Presence:** the user is online only while the app is in the foreground.
  `AccountStore` writes `online: true` plus `lastOnline` every 60s (`UserAccount.heartbeat`) while active. It writes `online: false` when the app goes to background or the user signs out.
  `UserAccount.isOnline(at:)` also needs a fresh heartbeat, so a killed app shows offline after about 2.5 minutes. The UI shows "Online now" or "Active 5m ago" (`LastSeenFormat.presence`) and refreshes through a `TimelineView`.
- **Dashboard:** days played together (distinct `playDays`), games played, minutes played, your love's presence, and matched since. The Scoreboard has its own tab.
- **No Firebase config?** Without `Config/GoogleService-Info.plist` the app uses `LocalAccountBackend`. The login button reads "Continue with test account". Requesting any unknown valid ID creates a pretend "Test Love", who accepts after 2s. Tests pass `pretendLoveReplyDelay: nil` and drive both sides with two stores on one backend. Unit tests use this backend too.

### Firebase setup (project: **PwL-application**)
1. Firebase console → PwL-application → Add app → **iOS**, bundle ID `com.khoadinh.PwL`.
2. Download `GoogleService-Info.plist` and put it at `Config/GoogleService-Info.plist`. The "Firebase config" build script copies it into the app.
   Copy its `REVERSED_CLIENT_ID` into `GOOGLE_REVERSED_CLIENT_ID` in `project.yml` (already done for pwl-application), then run `xcodegen generate`. That value becomes the Google sign-in URL scheme in `Config/Info.plist`.
   Without the scheme, GoogleSignIn raises an exception and the app crashes. `FirebaseAccountBackend.signIn` checks for it first and shows "Sign-in isn't set up yet" instead. Never inject the scheme from a build script: Xcode can regenerate Info.plist afterwards and drop it.
3. Authentication → Sign-in method → enable **Google** and **Email/Password** (Email/Password powers PwL ID sign-in).
4. Firestore Database → create the database (production mode) → Rules → paste `firestore.rules` → Publish.
5. Build and run. The login button now says "Continue with Google".
